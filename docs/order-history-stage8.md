# 第8段階：受注の要対応・キャンセルと写真管理

## 今回の範囲

これまで合意した、受注詳細からの結果操作、未処理伝票の継続表示、理由付きキャンセル、スマホからの写真保存、PCの写真一覧を追加した。既存の受注フォーム・配車・添付・権限・version付き共通保存・履歴を再利用する。LINEからの過去写真の移行や外部公開は含まない。

## 業務の流れ

| 操作 | 処理 |
| --- | --- |
| 担当伝票で完了 | 同じ伝票・作業日の全班を完了にし、受注に完了状態を記録 |
| 担当伝票で搬入不可・日延 | 全班の報告を揃え、受注を訪問日未定・要対応にする |
| 事務側で結果を入力 | 受注詳細のフッター「結果・キャンセル」。配車がある日は既存の全班報告を利用し、未配車でも事務側で結果を記録できる |
| 再訪問を決定 | 既存の受注編集で訪問日を入力・保存すると、要対応を解除。再配車は既存操作で事務側が行う |
| 正式キャンセル | お客様都合・搬入不可・荷主都合・重複受注・その他を選択。その他は詳細必須。通常一覧・担当一覧・配車ボードから除外し、受注の対応状況「キャンセル」「すべて」で参照可能 |

搬入不可・日延でも、実際に訪問した日付は配車と報告ログに残す。`last_work_date` に対象日を記録し、次の予定である `orders.visit_date` と訪問時間だけを未定にする。要対応は訪問日／登録日の検索期間外でも受注一覧に含める。新規の訪問日未定伝票とは「要対応」の表示で区別する。

同じ受注の別の作業日や既に決め直した訪問予定へ、古い報告を上書きしない。既存の過去報告は一括変更せず、新たな報告・訂正から今回の処理を適用する。キャンセルの取り消し専用機能や、新旧伝票を結ぶ再発注機能は追加していない。

## 状態・履歴・整合性

- 既存の `State`（標準・完了・削除）は置き換えず、受注に `order_status` を追加。`ACTIVE`、`NEEDS_ACTION`、`COMPLETED`、`CANCELLED` を使用。キャンセルは削除ではない。
- 結果・理由・取消理由・対象日・要求IDを受注と `orders_log` に記録。事務操作は受注のversion、現場操作は割当と結果のversionおよび作業日を確認する。
- 全班の報告と受注状態の変更は同一トランザクション。受注更新・履歴記録の失敗時も全体を取り消す。
- 作業報告の履歴に加えて、受注状態・予定日の変更を既存 `ORDER_SAVED` の差分として表示する。各班への反映で業務履歴を重複させず、既存の結果ログは各班に残す。
- キャンセル時に過去の配車・商品・写真は消さない。再訪問日の配車済み件数は、その日付に一致する有効な班だけを数える。
- 事務操作には既存の受注更新テーブル権限、`order.save` 操作権限、データ範囲を要求する。営業所共用アカウントは従業員IDを作らず、実際のアカウントをeditorに記録する。

## 写真の操作

- 担当伝票：「写真・添付」タブ。分類と対象訪問日を選択し、「撮影」または「写真を選択」。同じ伝票の担当班で共有。
- 受注詳細：「写真」タブから保存・参照。「添付」タブにも既存の添付として残り、分類・日付のフォルダに整理される。
- PC受注画面：「写真一覧」タブ。受注ID・分類・対象日で絞り込み、縮小画像を選択して拡大。前後移動・原本表示に対応。
- 分類は見積もり・施工前・完了・搬入不可・その他。対象訪問日・保存日時・保存者を記録する。保存日時は撮影日時とは別。
- JPEG・PNG・GIF、1枚20MB・1回20枚・合計90MBまで。JPEGの向きは縮小画像にも反映し、原本は変換しない。HEIC変換は未対応。
- 一覧は100枚ずつ読み込む。既存添付の画像も表示し、分類・対象日・保存者のない過去画像は未設定として扱う。
- 乗務員は担当伝票APIと同じ本人の担当範囲に限定。事務用受注権限を乗務員へ追加しない。元画像・縮小画像・既存添付の直接URLにも受注範囲の確認を適用する。
- スマホの書込み許可は専用の写真追加APIだけに限定。一般的な受注編集・取消・添付編集の制限は維持する。
- 通信失敗時は選択した写真を同じ画面内で保持し、「未保存の写真を再送」で同じ要求IDを使う。保存済みの要求は同じ添付IDを返し、重複保存しない。別の伝票へ詳細を切り替えても保存先は変えない。
- 写真の保持は画面内のメモリーのみ。再読込・ページ移動の前に保存／再送を終える。オフライン保管やバックグラウンド同期は追加していない。
- DB処理のロールバック時は作成した実ファイルも除去する。プレビューは縮小表示用で、原本の公開URL化や公開ストレージ化は行わない。

画面構造はThymeleafの共通HTMLフラグメントに置き、JSは表示更新・イベント・既存API連携を担当する。CSSはremを使用する。

## DB移行

`database/schema/20261101_order_followup_photos.sql` を開発DBに適用済み。受注・受注ログに業務状態を追加し、添付に写真メタデータと再送用の要求ID・順序を追加。既存結果の従業員IDは共用アカウント向けにNULLを許可する。既存データを削除しない。

別環境へ反映する場合は、先に同SQLを適用してからアプリを更新する。今回、本番への反映は行っていない。

## 画面での確認手順

1. アプリ再起動後、ブラウザーをキャッシュなしで再読込する。
2. 担当伝票で日延／搬入不可を報告し、事務側の受注一覧で「要対応」と訪問日未定を確認。検索期間を変えても残ることを確認する。
3. 受注編集で次の訪問日を保存し、要対応が解除されることを確認する。再配車は別途既存操作を使用する。
4. 受注詳細の「結果・キャンセル」で正式キャンセルを記録し、通常一覧から消え、「対応状況：キャンセル」で参照・履歴確認できることを確認する。
5. 担当伝票の写真タブで分類・対象日を選び撮影し、「保存しました」を確認。PCの写真一覧と受注詳細の添付から同じ画像を確認する。
6. 未保存写真がある場合は再送を完了し、原本・分類・対象日・保存者と拡大表示を確認する。
