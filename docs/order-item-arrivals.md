# 商品の入荷履歴

## 操作

商品一覧の「入荷」から日付と今回の数量を入力する。数量の初期値は残数。
「入荷済み 2 / 3、残り1」のように表示し、全数入荷後はボタンを「履歴」にする。
登録・訂正・取消後は完了ダイアログを表示する。

PCでは履歴ごとに訂正・取消できる。訂正時は元行を取消扱いにして新行を追加し、
元の日付・数量・登録者を残す。物理削除はしない。
スマホでは新しい入荷の登録と履歴の閲覧のみ。訂正・取消はPCで行う。
このスマホ制限は既存方式に合わせた画面・リクエスト制御であり、端末を認証する権限制御ではない。

商品新規・編集フォームには「入荷予定日」を設ける。新規商品は未入荷として保存し、
実際に受け取った時点で一覧から入荷登録する。入荷実績の日付は直接入力で上書きしない。
予定日は商品行全体の予定として1つ保持する。便ごとの予定管理は今回の対象外。

入荷状態の「未入荷」絞り込みは従来の未完了条件を維持し、一部入荷も含む。
「一部入荷」では数量が0より多く全数未満の商品だけを表示する。
一覧の「受注未設定・工事未完了・入荷未完了」の掲載条件は維持している。

## 保存と整合性

- `order_item_arrivals` に数量・日付・登録者・登録日時・訂正元・取消情報を保存。
- `order_items.expected_arrival_date` は予定、`arrival_date` は全数入荷時の最終入荷日。
  一部入荷・未入荷では `arrival_date` をNULLにする。
- `/api/query` の `orderItemArrivalDetail` で商品と履歴を取得。
- `orderItemArrival` / `orderItemArrivalCorrect` / `orderItemArrivalCancel` が登録・訂正・取消。
- `orderItemSave` / `orderItemCreate` と受注フォーム内の既存商品更新も共通サービスを経由。
  入荷累計以下への数量変更は拒否する。入荷履歴がある商品を増数した場合は未完了に戻る。
- 商品行を `UPDLOCK, HOLDLOCK` でロックし、履歴保存と商品更新を同じトランザクションで行う。
  商品のversionも確認・更新するので、同じ画面状態からの競合登録は再確認を求める。
- UUIDの要求IDで同じ要求の再送を識別する。通信結果が不明な場合は画面が履歴を再取得する。
- 数量は正の整数、入荷日は当日以前。入荷実績の合計は商品数量を超えられない。

## DB反映手順

アプリの起動前に `database/schema/20260912_create_order_item_arrivals.sql` を適用する必要がある。
SQL未適用のまま新版を起動すると商品一覧・受注商品保存でエラーになる。

1. 対象DBをバックアップし、旧アプリからの書込みを停止する。
2. SQLを対象DBで実行する。予定日の列（商品と商品ログ）と入荷履歴テーブルが作成される。
3. 既存の入荷日がある商品は、現在の数量を全数入荷とした履歴を1件作る。
   過去の分割状況は復元できない。登録者は「既存データ移行」。
   入荷済みで数量がNULL・0以下の行があれば、移行全体を中断する。
   対象行の数量を確認・修正してから再実行する。
4. 新版アプリを起動し、以下の動作を検証する。

再実行時には既存テーブルを再作成せず、移行履歴も重複登録しない。
初回移行後に旧版で入荷日を変更しないこと。履歴導入後に旧版へ戻す場合は、
新版で書き込んだ履歴も含めた整合性の確認が必要。

## 確認

自動テスト: 分割入荷、全数入荷、訂正、取消、重複要求、古いversion、数量超過、
商品数量の減少制限、予定日保存、モバイルの訂正・取消制限。

実DB・実機で次を確認する（今回の作業環境では未実施）:

1. 数量3の商品に2を入荷登録し、残数1と一部入荷表示を確認。
2. 残り1を登録し、全数入荷日と「履歴」表示を確認。
3. PCから片方を訂正・取消し、元履歴の保持と残数・入荷日の再計算を確認。
4. PCから入荷済み数量未満へ商品数量を変更すると保存されないことを確認。
5. 同じ商品を2画面で開いて登録し、後から保存した画面が競合エラーになることを確認。
6. スマホで入荷登録はでき、訂正・取消が表示されないことを確認。
7. 既存受注フォームから商品数量を変更し、履歴と整合性が保たれることを確認。
