# 伝票履歴 第3段階：受注基本情報の変更前後

## 実装

既存のorderHistoryList APIを拡張し、orders_logのスナップショットから変更前後を取得する。order_historiesに値を複製せず、テーブル追加・DDL変更・共通保存処理の変更は行わない。

- 先に受注参照権限・ALL/OWN/ASSIGNED/OWN_ASSIGNED・カーソル条件を適用し、最大100件をhistory_pageとして選ぶ。
- 履歴のorder_id/order_versionと一致する保存後ログ、および同一受注のversion - 1に一致する保存前ログをOUTER APPLYで取得する。直近の古いログへ飛ばして比較することはしない。
- COUNT(*) OVER()で候補数を返す。両側がそれぞれ1件の場合にだけフロントで差分表示する。ログ欠落・重複時は確認できない旨を表示し、履歴自体は残す。
- 対象は受注番号、お客様名・件名、郵便番号、住所、訪問日、訪問時間、連絡先、備考の8項目。訪問日はSQLでYYYY-MM-DDの文字列にそろえ、ブラウザーのタイムゾーン変換を避ける。
- ORDER_SAVEDのみ比較し、値の変わった項目だけ「変更前」「変更後」で表示する。nullと空文字は未設定として同一視するが、空白・改行は保持する。削除した値は（未設定）と表示。
- 表示対象8項目が同じなら、その範囲で変更がない旨を表示する。商品・作業だけの変更や担当営業所などの変更を「保存がなかった」と解釈しない。
- ORDER_CREATEDと将来の未知のイベントでは保存前の差分を生成しない。差分値はtextContentで描画し、HTMLとして解釈しない。
- 既存の履歴スクロール領域をそのまま利用。追加スタイルはrem単位。担当伝票一覧や詳細画面の直前までの表示調整を保持。

## 検証

- Java: 200件中191件成功、既存9件スキップ、失敗・エラー0。
- JavaScript: 111件すべて成功。追加6件で、複数項目変更・値の削除・null/空文字・改行・欠落/重複ログ・新規イベント・対象項目に変更のない保存・HTML非解釈を確認。
- Javaテストは既存Mockito 5.14.2のjavaagentを指定して実行。依存関係やpomの変更なし。
- 開発DB NeoDBのorders_log列・型を読み取り確認。新しいSQLを実際のJDBCドライバーで実行し、ALLで履歴3件の取得、存在しない営業所・従業員を指定したOWN/ASSIGNEDで0件、カーソル指定時に重複しないことを確認。個人情報の値は検証ログに出力していない。
- 検証でDBデータの登録・更新・削除はしていない。実ブラウザーからの変更保存→差分表示の一連の操作は未確認。

## 利用確認

バックエンドのソース変更を反映するため、必要に応じて再ビルド・アプリ再起動を行う。画面も再読み込みする。

1. 既存受注の住所や訪問日時を変更して保存する。
2. 受注詳細を開き直し、「履歴」で変更前と変更後を確認する。
3. 備考を消して保存すると変更後が（未設定）になることを確認する。
4. ログの欠けた古い履歴でも、履歴一覧そのものは表示できることを確認する。

既存DBには第1段階のorder_historiesが作成済み。今回のための追加SQLの実行は不要。デプロイはしていない。

## 残作業

商品・作業明細の差分、担当営業所・荷主・担当者などの名称付き差分、配車変更、搬入不可・日延・完了・直収の業務イベント、PDF別登録経路・明細単独APIの履歴追加、過去ログ移行は未着手。大規模な履歴ではorders_logの(order_id, version)索引と実行計画の評価も別途行う。
