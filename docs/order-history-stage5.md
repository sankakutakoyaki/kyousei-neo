# 担当伝票の作業結果操作

## 取り決めと範囲

最初の方針どおり、作業結果は訪問・配車単位で管理し、受注全体の状態と分ける。結果の保存と業務履歴は同じトランザクションで処理し、訂正前の結果をログから消さない。

今回の操作は「完了」「搬入不可」「日延」の報告と訂正。担当伝票詳細にボタンを追加した。搬入不可・日延は理由を必須とし、完了の初回報告は備考を任意とする。登録後の結果を訂正する場合は種類を問わず訂正理由を必須にする。

ユーザーの追加指定に従い、次回予定日の入力欄は設けない。希望日などを聞けた場合は作業結果の「理由・備考」に記入する。受注の訪問日の確定・配車解除・再配車は事務側の操作とする。受注の共通備考欄も自動上書きしない。

## 現在の結果と履歴

`order_work_results` は（配車割当ID、訪問日）ごとの現在の報告を保持する。配車移動などで訪問日が変わっても以前の完了結果を次の訪問日に引き継がない。画面の訪問日は班の作業日を使用する。

更新時は既存BaseSqlRepository / SqlBuilder / GenericLogSqlProviderを利用して、`order_work_results_log` に保存後の全項目を記録する。現在値のversionを使って更新競合を拒否する。共通SqlBuilderの変更はしていない。

`order_histories` には結果ID・結果versionの参照を追加し、WORK_COMPLETED / DELIVERY_FAILED / POSTPONED / WORK_RESULT_CORRECTEDのイベントを記録する。結果値を履歴へ二重保存せず、表示時に結果ログの正確なversionを参照する。訂正時は一つ前の結果versionと比較する。

## 権限・排他・再送

担当伝票の既存MyOrderControllerと同じAPPROLE_userの認証条件を維持し、既存の専用APIを拡張する。

- GET/POST `/api/my-orders/{orderId}/assignments/{assignmentId}/result`
- 有効な班・班員・配車・受注と、ログイン従業員の一致をサーバーで確認する。
- 保存は班→割当の順にロックし、取得後に担当と班を再確認。既存配車操作のロック順に合わせる。
- 配車version・訪問日・結果versionを確認する。担当変更、配車解除、訪問日の変更、他の社員による結果更新後は古い画面から保存できない。
- requestIdはUUID。確定済みの結果ログで照合し、同じ内容の再送では結果と履歴を追加しない。別の配車・訪問日・内容への同じUUIDの流用は拒否する。
- 報告者IDとログの操作者はサーバー側の既存OwnOfficeContextServiceから取得する。
- 履歴保存の失敗は握り潰さず、結果・ログを含めてロールバックする。

## 画面

既存のdata-actionとコントローラーから作業結果用の小さな入力部品を開く。結果入力は元の伝票詳細の閲覧専用フィールドと分けたネイティブdialogに置き、スマートフォンでも理由・備考を入力できるようにする。既存apiFetchでCSRF・HTTPエラー処理を再利用する。

報告済みの結果はカードに表示し、一覧上部に総件数と未報告件数を表示する。同じ受注が複数の配車割当に含まれる場合も、割当IDを使って対象を選択する。結果の取得中に伝票を切り替えた場合は古い入力画面を開かない。保存中の連打・閉じる操作を抑止し、通信エラー後の同じ内容の再試行には同じrequestIdを使用する。

モバイルの書込許可は上記の厳密な結果POSTパスのみ追加し、受注編集・配車編集などの一般的な書込許可は広げない。追加CSSはremを使用する。

## DB適用

`database/schema/20261031_create_order_work_results.sql` を第4段階のSQLの後、アプリ更新前に適用する。現在の結果と既存方式のログを作成し、履歴参照列・イベント制約・フィルター付き一意索引を拡張する。

開発中に作成した未公開・空の検証テーブルに訪問日のキーがない場合だけ、訪問日単位のキーへ調整し、不要になった次回予定日の列を整理する。既存の結果データがある場合は日付を推測して移行せず中断する。

## 確認した内容

Javaは213件中204件成功・既存9件スキップ、JavaScriptは120件すべて成功。既存テストと結果保存・入力部品のテストを実行。担当外拒否、配車・結果の競合、訪問日変更後の古い画面の拒否、理由必須、訂正、同じ要求の再送、二重クリック、希望日専用欄を持たないことを検証した。

VPN経由で開発DB NeoDBに最終仕様のDDLを適用済み。既存の共通保存・ログ・履歴処理を組み合わせ、完了→搬入不可への訂正→日延への訂正、再送抑止、古いversion拒否、履歴取得を確認し、検証データをトランザクション全体でロールバックした。アプリの接続設定は変更していない。ブラウザーからの一連の操作は未確認。

## 今回の対象外

受注全体の自動完了、日延時の訪問日変更・配車解除・再配車、結果の取消による未報告への復元、全件報告後の日次業務確定、直収・代引き・入金の処理、担当伝票側の履歴タブは追加していない。

アプリを再ビルド・再起動し、画面を再読み込みする。担当伝票の詳細から結果を選択し、理由・備考を入力して保存する。カードの状態・未報告件数の更新と、受注詳細の履歴を確認する。希望日などのメモは結果の理由・備考として残り、受注の訪問日や既存備考・配車は自動変更しない。
