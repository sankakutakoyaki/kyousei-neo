# 配車

## 調査・仕様

- 元の `/Users/makoto/Git/kyousei-neo` は調査時点で未コミット変更なし。新しい作業場所と同じ `37fd8b9`。元の作業場所への書き込みなし。
- `orders.staff_id` は小売業者・支店に紐づく営業担当者（`staffs`）。配車担当へ転用しない。
- 作業者は `employees` の社員(1)、アルバイト(2)、請負(3)。協力会社との関係は `company_id`。有効な従業員と所属会社を候補とする。会社だけの割り当てではなく、登録済みの個人を選ぶ。
- 配送・工事は別区分で各複数名。同じ人を両区分に割り当て可能。両区分を合わせて最大100件。
- 日程は既存の `orders.visit_date` / `visit_time` を共用。配車画面では変更しない。作業明細 `order_works` には別日程を追加しない。
- 業務メニューの「配車」で訪問日期間（最大93日）、日程未定、未割り当て、番号・件名・住所・担当者等の文字検索に対応。日程未定はチェック時だけ含む。
- 標準受注(0)は編集可能、完了(2)は閲覧のみ、削除は対象外。
- 画面と `/api/query` の配車操作は既存受注と同じ admin / master / leader / staff / user が利用可能。PC編集も同じ。スマホ編集は勤怠管理と同じ admin / master / leader のみ。
- スマホ判定は既存の画面幅・ポインター判定に加え、サーバーで User-Agent と Sec-CH-UA-Mobile も検査。端末情報自体はクライアント由来なので、偽装されたPC要求と真のPC要求を厳密には識別できない。ロールはサーバーの認証情報から取得する。

## HTMLの構成

既存と同じ `content.html` / `header.html` / `form.html` に分割。タブ、`table-area`、検索用の共通 inputBox / selectBox / dateRange、一覧の `fragments/table/body`、件数フッターを使用。PCは表、スマホは同じ表の行をCSSでカード表示する。割り当ての複数選択だけは専用のチェックボックスを生成する。ダイアログは共通header/footer、保存はFormController、確認はDialogServiceを継続利用。

## 保存と履歴

`DispatchQueryProvider` / `DispatchHandler` を既存 QueryId / QueryKind に登録し、`DispatchService` から `SqlRepository` を使用。フォームは `FormController`、共通header/footer、`DialogService.confirm` を利用。

受注行をトランザクション内でロックし、受注versionと配車専用versionを検査する。異なる利用者による古い画面からの保存を拒否。既存受注データは変更しない。新規割り当てと解除を同一トランザクションで反映する。解除は物理削除せず、時刻・認証済み編集者を保存。加えて `DispatchLogSqlProvider` がSQLのOUTPUTで変更後の全列を取得し、`order_dispatch_assignments_log` に `editor`・`process`・`log_date`・`dispatch_version` とともに保存する。登録はINSERT、解除はUPDATE。1回の保存で変更された担当者は同じ配車更新番号を持つ。変更のない保存はログを追加しない。履歴の氏名は登録時スナップショット。

無効化された従業員の既存割り当ては履歴とともに維持・解除できる。新しい割り当ては禁止。保存失敗時は画面を閉じず共通ダイアログで知らせる。担当者の日程重複・車両・経路の自動調整は今回の対象外。

ログ導入前のレコードは、ログ追加SQLで現在状態を `MIGRATE` として記録する。過去の登録・解除日時は元の列に残し、移行日時と区別する。既存割り当てテーブルは変更しない。ログテーブル作成済みの場合は移行処理を繰り返さない。

配車で使用する `SqlRepository.update(String, List)` は `DataSourceUtils` 経由でトランザクションに参加する。更新・ログ・配車更新番号の保存が途中で失敗すると全体をロールバックする。

## DB適用手順

実DBには未適用。アプリの自動移行機構には登録していない。

1. 対象SQL ServerのDBを確認しバックアップ、アプリを停止する。
2. `orders.order_id` と `employees.employee_id` が INT 主キーであることを確認する（リポジトリには元テーブルの完全なDDLがない）。SQL Server 2017以降の STRING_AGG が利用できることを確認する。
3. `database/schema/20260913_create_order_dispatch.sql` を対象DBで実行する。新規2テーブル・外部キー・有効割り当ての一意索引を作成。続けて `database/schema/20260913_add_order_dispatch_log.sql` を実行し、ログテーブルを追加する。最初のSQLを適用済みの場合はログ追加SQLだけ実行する。既存受注・営業担当・日程データの更新はない。スクリプト全体はトランザクション、再実行可能。
4. アプリを起動。業務→配車で検索し、社員と請負それぞれの選択、両区分複数名、解除、履歴を確認する。
5. 同じ伝票を別画面から保存し、古い画面では競合として拒否されることを確認する。受注側の日程変更でも古い配車画面からの保存は拒否される。
6. PC、スマホ管理者、スマホ一般利用者で表示・保存を確認する。削除済み・完了受注、権限外アカウントも確認する。

アプリだけ戻す場合、追加テーブルを残しても既存機能に影響しない。運用後にテーブルを削除すると配車履歴を失うため、戻す場合もバックアップを保全する。
